# README

## 1. サービス概要
文字入力殆どなくし、学校プリントのタスク登録がすぐに完了、情報共有がスムーズに行えるアプリです。

カレンダーやフォルダ分類などの多機能さをあえてなくし、対応期日が近い順にプリント画像が並ぶだけの「挫折しないミニマル設計」に特化しています。

## 2. このアイデアはどこから生まれたか
### 2-1. きっかけとなった体験・感情
長女が小学校に入学した際、保育園時代とのギャップによる配布物管理の負担に苦労したことがきっかけです。
保育園ではお便りはアプリ配信、提出物も先生からのリマインドがありましたが、小学校では毎日大量の紙プリント（学級だより、全校お知らせ、給食だよりなど）が配られ、リマインドも一切ありません。
提出期限や持ち物の情報が各プリントに散散しているため、必要な情報を探す時間が大きなストレスでした。
また、仕事で帰宅が遅い夫にすべてのプリントを読んでもらうのは難しく、管理負担が私一人に集中し、心身ともに大きな重荷となっていました。

### 2-2. なぜそれが「気になった」のか
私の中で、「在宅時間が長いから現状として私が家事・育児を多く担っているだけであって、家事・育児は私（妻）だけの仕事ではない」という強い思いがあるからです。
夫が家庭にコミットできるタイミングは、必ずあるはずと考えています。
また、万が一自分が体調不良などで動けなくなったときでも、家庭が円滑に回り続けるためには、夫婦間のフラットな情報共有が不可欠です。
学校からの大切なお知らせをブラックボックス化させず、「夫婦が同じ目線で、いつでも把握できる環境」を作りたいと考え、本アプリの開発を決めました。

## 3. 課題の整理
### 3-1. 表に見えている困りごと
学校からの大事な提出期限や持ち物の情報を見落とさないように管理できず、把握しきれないこと。

### 3-2. 本当に解決したい課題
なぜ？：子供が学校生活で困ったり、先生に迷惑をかけてしまったりするから。

なぜ？：迷惑をかけないために自分1人で完璧に管理しようと抱え込み、脳内疲労が生まれるから。

なぜ？：情報が自分にしか集約されていないため、夫に頼むことすらできず責任が集中するから。

解決したい課題：プリント管理の属人化をなくし、複数人（夫婦）でシームレスに共有・管理できる状態を作ることで、個人の負担を軽減し、時間と心の余裕を生み出すこと。

## 4. 想定ユーザーについて
### 4-1. 想定しているユーザー
年齢・状況：20代〜40代の子育て世代。
特に小学校入学時、「小1の壁」（たくさんのプリント管理に悩んでいる）世帯。提出物やお金の管理をほぼ親が管理することが必要で、負担になっている状況。

課題へのアプローチ：
日々の多忙さから、ゆっくり夫婦で情報共有する時間がない状況に対し、「文字入力を一切させない（写真を撮ってタグを選ぶだけ）」という仕組みを提供し、疲れた夜でも挫折せず継続できるようにします。
また、登録時に「出してね」「用意してね」など次の行動（アクション）がひと目でわかるタグをセットにするため、すぐに「すべき行動」を把握できます。説明コストを減らし、負担なくタスクが共有される環境を作ります。

### 4-2. 自分とユーザーの距離
距離感：自分自身、および身近な方（夫、ママ友など）

理由：私自身が直面しているプリント管理の限界は、同じ環境にいる子育て世代にとって共通の深い悩みであり、当事者だからこそ「本当に必要な最小限の機能」を追求できるから。

### 4-3. 実際に使われる可能性について（需要・存在確認）
既存の代替手段と置き換える理由：
現在は「紙プリントをそのまま共有する」「壁掛けカレンダー」「家族LINE」が主流ですが、外出先で見られない、会話に画像が埋もれる、そもそも多忙な夜に1から手入力でアプリに登録する余裕がない、といった課題があります。
本アプリは、文字入力なしの4タップですぐに登録できるため、日々の登録ハードルを下げて、管理の負担を減らします。
また、プリントは締め切り（対応日）順に一覧で並び、タグでするべき行動（提出する・用意するなど）が表示されるほか、本リリース以降は「新着」と「直近のタスク」を仕事終わりの夕方～夜間に1日1度まとめて通知する機能も実装予定です。それにより、日中のノイズにならないタイミングでやることが視覚的に届くため、忙しくて育児にコミットできなかったパートナーも情報の把握ができ、主体的に参加できるようになります。
既存の方法では課題だった、情報の属人化・負担の偏り・情報把握の困難さといった問題が、本アプリのこれらの機能連携によって解決されると考えています。

### 4-4. ユーザーがサービスを導入して利用するまでのイメージ
導入のハードルを下げる工夫：ユーザー登録時に、できるだけ入力内容を減らしシンプルにしました。（ユーザー名、メールアドレス、パスワード、家族コードのみ）
また本リリースでは、ユーザー名の登録もなくしアイコン選択（もしくは任意画像の登録）で行い文字入力の負担を減らします。
そして、家族招待機能を実装しパートナーの登録負担も減らします。

## 5. 既存サービス・競合調査
### 5-1. 似たサービスの調査
おたよりクリップ：画像登録、タグ付け、フォルダ分類が可能。

本アプリとの違い：分類・整理ができる反面、マメな入力が必要で多忙な時期に挫折しやすいのではないかと感じる。


プリゼロ：カレンダー連携、リマインド、OCR（文字認識）など非常に多機能。

本アプリとの違い：多機能な反面、画面の情報量や設定項目が多く、使いこなすまでの認知コストが少し高く感じる。

### 5-2. それでも自分が作りたい理由
既存アプリは「マメに管理できること」を前提とした設定項目が多く、入力作業自体が新たな「重いタスク」になっていると感じていました。「綺麗な整理・管理じゃなくていいから、すぐにプリントを放り込めて、期限だけを見落とさないツール」が欲しいと感じたため、開発を決意しました。

### 5-3. 差別化を一文で決める
「毎日大量のプリントとマルチタスクに追われる親が、疲れた夜でもすぐに登録できて、パートナーと一緒に『小1の壁』を乗り越えられるプリント管理アプリ」

## 6. このサービスで提供したい価値
ユーザーの変化：プリント管理の煩雑さから解放され、「自分しか知らない」というワンオペ状態から解放されます。
時間・精神的な余裕が生まれます。管理は「ママの仕事」ではなく「夫婦のタスク」という認識に変わります。

価値を一文で表す：育児の負担が偏っている人たちが、配布物管理のストレスと情報の孤独から解放されて、夫婦でフラットに家庭運営を行えるようになるサービス。

## 7. このアプリで実現すること（機能要件）
### MVPで作る機能
ユーザー登録・ログイン機能（家族コード連携）：メールアドレス、パスワードによる認証。ユーザー登録時に共通の「家族コード」を入力することで、同一家族間でデータを共有。
文字入力ゼロのプリント画像登録機能：「写真選択」「子どもタグ選択（第1子〜第4子）」「期限日選択（1つのみ）」「アクションタグ選択（1つのみ）」の4タップで登録。
  アクションタグの種類：
    出してね（提出が必要）
    用意してね（持ち物準備）
    現金いるよ（集金・引き落とし情報）
    当日見てね（イベント・行事の詳細）
    読むだけでOK（お知らせ・チラシなど）
期限順一覧表示機能（ダッシュボード）：登録された画像が、設定した期限の近い順にカード形式で並ぶ。

### 本リリース以降に実装する機能
画像編集機能（マーカー・ライン）
アクションタグの複数選択・個別対応日設定機能
「既読」マーク・「対応済み」ボタン
家族招待機能
パスワードリセット機能
「子どもタグ」を任意の名前表示に変更できる機能
「子どもタグ」ごとに「プリント一覧」を切り替える機能
リマインド機能（１日1度「新着」と「直近タスク」を通知。通知時間は夜間～夕方にデフォルトで設定。時間設定は任意で可能に）
カレンダー連携
キーワード/タグ検索機能

## 8. このアプリの懸念点とその対策
懸念点：「文字入力をさせない（タイトルがない）」仕様のため、枚数が増えた際、年間予定表などの「長期保管したいプリント」を画像一覧から探しにくくなる可能性がある。

対策：MVP時は、直近の締め切り（当月内など）のプリントのみを優先表示し、終わったものはすぐ削除する運用でカバーします。本リリース以降に「長期保管用フラグ（ピン留め機能）」や「タイトル検索」を追加し、検索性を補完します。

## 9. 今後の展開・発展の方向性
子供が卒業するまで毎日発生する配布物に対し、生活の必須インフラとして機能させます。「タスク管理がラクになった」という成功体験をベースに、他の家庭内タスクの共有へと繋げます。

## 10. 技術スタック
### 10-1. 使用予定の技術
フレームワーク：Ruby on Rails8, JavaScript

DB：PostgreSQL

主要ライブラリ：Sorcery,CarrierWave,MiniMagick,Kaminari

デプロイ先：Render

ストレージ：AWS S3

### 10-2. 技術選定の理由
MVPの必須機能（CRUD、認証）はすべてRailsでの実装実績があり、バグの自己解決が容易なため。

限られた開発期間の中で、新しい技術の学習コストを抑え、確実に実装するため。

将来的な拡張（メール通知等）もRailsの標準機能で柔軟に対応可能なため。

### 10-3. キャッチアップ不足の懸念
限られたスケジュールの中で確実に形にするため、まずはカリキュラム（基礎編）で練習したRailsの基本機能を使って、MVPの確実な完成を最優先にします。

MVP完成後は、本リリースに向けて「タグでの切り替え」や「編集機能」の実装を通じ、カリキュラムの応用編への理解を深め、技術的にステップアップします。

まずは土台をしっかりと構築し、その後は応用編の課題や新しい技術にも一歩一歩キャッチアップを続け、アプリをより使いやすく育てていく計画です。
